# App Monitor MCP Server - Implementation Specification

**Date:** 2025-11-17
**Status:** ✅ APPROVED - Ready for Implementation
**Total Tools:** 24 (Plan: 11, Task: 6, Bot: 4, PR: 2, System: 1)

---

### Scope Update — November 20, 2025

The initial approval covered 24 tools, but the first MCP release intentionally ships a smaller, testable surface area:

- Plan management tools are **deferred** until the existing planning system is reliable.
- Task APIs expose creation, inspection, manual resume, and dev-bot outcome reporting only. Cancellation, reprioritisation, and log access remain backend-only.
- System diagnostics are limited to the `system_health` tool. Additional metrics/log/restart tools stay out-of-scope so bots continue reading logs directly.
- The MCP server always starts with the backend (no feature flag) and only runs over stdio on the local host so it is never exposed via Cloudflare/nginx.
- Role-based access relies on `APP_MONITOR_MCP_USER_ROLE` (`admin` vs `dev-bot`) with dev-bots blocked in production environments.

The remainder of this spec keeps the original design details for future phases, but any sections describing deferred tools should be treated as references, not current scope.

## Quick Reference

**What:** MCP server embedded in backend providing structured agent access
**Who:** Admin bot (full access), Dev-bots (limited access), Humans (via Claude Desktop)
**Where:** `backend/src/mcp/` - runs as part of backend process
**Deploy:** Auto-deploys with backend via blue-green (temporary reconnection)

## Architecture

### Embedded in Backend

```typescript
// backend/src/server.ts
import { startMcpServer } from './mcp/server.js';

async function main() {
  // Start HTTP API
  const app = await startExpressApp();
  app.listen(PORT);

  // Start MCP server (stdio)
  await startMcpServer({
    db: getDatabase(),
    services: getServices()
  });
}
```

**Benefits:**
- ✅ Shares database/services (no duplication)
- ✅ Version always matches backend
- ✅ Single deployment process
- ✅ MCP changes deploy with backend

### Blue-Green Deployment Handling

1. Blue (port 5001) running with admin bot connected
2. Green (5002) starts → health checks pass → nginx switches
3. Blue shuts down → admin bot sees connection lost
4. Admin bot reconnects → connected to green
5. Clear message: "🔄 Backend deployed, reconnecting..."

## Access Control

### Three Environments

**1. Production MCP (Admin bot only)**
- Location: `/opt/app-monitor` backend
- Access: Admin bot, human operators
- Tools: All 24 tools (except `task_report_outcome`)

**2. Dev-Bot Test Environment MCP (Full access)**
- Location: Inside dev-bot container
- Access: Dev-bot only
- Tools: All 24 tools (isolated test environment)
- Purpose: Testing changes in isolation

**3. Dev-Bot Production API (Limited)**
- Dev-bots call production backend REST APIs for:
  - GET task details (their assigned task)
  - POST task outcome (report completion)
- ❌ Cannot create plans/tasks in production
- ❌ Cannot access production MCP server

### Permission Middleware

```typescript
const checkToolPermission = (tool: string, context: AuthContext) => {
  if (context.isDevBot && context.env === "production") {
    throw new Error("Dev-bots cannot access production MCP");
  }

  if (context.isAdminBot) {
    const disallowed = ["task_report_outcome"];
    if (disallowed.includes(tool)) {
      throw new Error(`Admin bot cannot access: ${tool}`);
    }
  }
};
```

## Approved Tools (24 Total)

### 1. Plan Management (11 tools)

#### Tool 1: `plan_create`
Create new plan with auto-generated YAML file

**Input:**
```typescript
{
  name: string,                    // Required
  type?: "feature" | "refactor" | "fix" | "investigation",
  priority?: "p0" | "p1" | "p2" | "p3"
}
```

**Returns:** `{ plan_id, file_path, version }`

---

#### Tool 2: `plan_get_status`
Get plan execution status (NOT file contents - agent reads file directly)

**Input:** `{ plan_id: string }`

**Returns:**
```typescript
{
  plan_id: string,
  status: "draft" | "researched" | "ready" | "in_progress" | "completed",
  batches: [
    { id, name, validation_state, can_import, tasks_total, tasks_completed }
  ],
  progress: { percentComplete, batches_completed, tasks_completed }
}
```

## Removed Tools (From Original Proposal)

**Plan Management:**
- ❌ `batch_import` - Backend-only, not for agents
- ❌ `plan_read` - Agent reads files directly

**Task Operations:**
- ❌ `task_get_logs` - Agent reads logs directly
- ❌ `task_update_priority` - Priority doesn't affect FIFO execution

**Dev-Bot Control:**
- ❌ `bot_get_assigned_task` - Redundant with bot_get_status + task_get
- ❌ `bot_get_logs` - Agent reads logs directly
- ❌ `bot_terminate` - Replaced with bot_recover

**PR Evaluation:**
- ❌ `pr_get_status` - Redundant with pr_trigger_evaluation
- ❌ `pr_force_merge` - NEVER bypass gates, human-only in GitHub UI

**System Diagnostics:**
- ❌ `system_get_metrics` - Covered by enhanced system_health
- ❌ `system_check_ports` - Deployment info in system_health
- ❌ `system_get_logs` - Agent reads logs directly
- ❌ `system_restart_component` - Not architecturally sound, use blue-green deployment
