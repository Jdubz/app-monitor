PART 1: EXISTING RECOVERY MECHANISMS (PRODUCTION-READY)
================================================================================

1. TWO-STAGE FAILURE RECOVERY SYSTEM ✅
   Location: backend/src/services/failureRecovery.ts (343 lines)
   
   Architecture:
   Task Fails
     └─> Check Recoverable (5 categories)?
           ├─> YES: Create Cleanup Task (Stage 1)
           │         - Fix ONLY the error
           │         - Constraint: <5 files, <100 lines
           │         - Priority: 100 (jump queue)
           │         
           └─> Cleanup Completes?
                 ├─> YES: Create Followup Task (Stage 2)
                 │         - Complete original goal
                 │         - Error already fixed
                 │         - Auto-created (event-driven)
                 │
                 └─> NO: Stop (no followup)
   
   Safety Guarantees:
   - No duplicate repairs (hasActiveRepair() check)
   - Circular prevention (never repair repair bots)
   - Minimal changes constraint (<5 files)
   - Protected files (package.json, .env, .db)
   - Fail-safe (followup only if cleanup succeeds)
   
   Recoverable Error Categories:
   ✓ cli_incompatibility      (flag fixes, version issues)
   ✓ missing_resource         (missing files, deps)
   ✓ syntax_error             (code problems)
   ✓ import_error             (module not found)
   ✓ config_error             (configuration issues)
   
   Metadata Tracking:
   - isRepairBot: true/false
   - repairStage: 'cleanup' | 'followup'
   - originalTaskId: parent task ID
   - cleanupTaskId: cleanup task ID (for followup)
   - originalFailurePattern: what error triggered recovery


2. SQLITE TRANSACTION-BASED TASK QUEUE ✅
   Location: backend/src/services/taskQueue.sqlite.ts
   
   Resilience Features:
   ✓ Atomic task assignment (no race conditions)
   ✓ ACID guarantees via transactions
   ✓ Worker heartbeat detection (identify crashed workers)
   ✓ Manual intervention (no auto-timeouts)
   ✓ Execution history tracking
   
   Philosophy:
   - Complex tasks may take hours (no auto-timeout)
   - Manual intervention via manuallyTimeoutTask()
   - Baseline learning mode: collect duration stats
   - After 50+ tasks, can enable smart timeouts


3. CIRCUIT BREAKER PATTERN ✅
   Location: backend/src/utils/circuitBreaker.ts
   
   Configuration:
   - Threshold: 5 consecutive failures
   - Reset timeout: 60 seconds
   - States: Closed (normal) → Open (fail fast) → Half-Open (testing)
   
   Benefit:
   - Prevents cascading failures
   - Fails fast when Docker daemon is down
   - Auto-recovery attempt after 1 minute


4. MANUAL RETRY MANAGER ✅
   Location: backend/src/services/retryManager.ts
   
   Features:
   - Manual retries only (not automatic)
   - Respects max_retries flag
   - Tracks retry history with reasons
   - No exponential backoff (kept simple)
   - Reset task to 'pending' for retry


5. TASK EXECUTION FLOW ✅
   Location: backend/src/services/taskExecution.service.ts
   
   Sequence:
   1. Atomic pull from SQLite queue
   2. Agent selection (personality-based)
   3. Prompt generation (context-aware)
   4. Docker container execution
   5. Output capture (stdout/stderr → task fields)
   6. Failure pattern detection (regex on output)
   7. Recovery trigger if recoverable


6. EVENT-DRIVEN TASK COMPLETION ✅
   Location: backend/src/services/taskCompletion.service.ts
   
   Triggers:
   - Recovery followup creation (if cleanup done)
   - PR workflow orchestration (if PR in output)
   - Task completion event (for listeners)


7. PR WORKFLOW ORCHESTRATION ✅
   Location: backend/src/services/prWorkflowOrchestrator.service.ts
   
   Features:
   - Extracts PR info from bot output
   - Registers PR for monitoring
   - Auto-merge when checks pass
   - Creates followup tasks if checks fail
   - Resumes on startup

PART 4: KEY FAILURE POINTS & MITIGATIONS
================================================================================

FAILURE POINT 1: Container Creation Fails
What: OOM, no disk space, image pull timeout
Mitigation: Circuit breaker (5 failures → 60s reset)
Gap: No type detection (OOM vs timeout)


FAILURE POINT 2: Workspace State Corruption
What: Uncommitted changes, merge conflict, detached HEAD
Mitigation: None (isolated containers)
Gap: No pre/post snapshots


FAILURE POINT 3: Agent Unavailability
What: Agent doesn't exist or isn't available
Mitigation: Check before execute, fail task
Gap: No fallback agent logic


FAILURE POINT 4: Output Capture Failure
What: Task runs but output not captured
Mitigation: docker cp to host, fail if that fails
Gap: No direct streaming, no database backup


FAILURE POINT 5: Recovery Loop Prevention
What: Cleanup fails → followup fails → another cleanup
Mitigation: Never repair repair bots (circular prevention)
Strength: WELL-DESIGNED ✓
Gap: No recovery attempt budget

================================================================================
PART 6: DESIGN DECISIONS (WELL-MADE)
================================================================================

✅ Two-stage recovery (cleanup → followup)
   Simple, proven, event-driven pattern

✅ Manual timeouts, not automatic
   Respects complex task durations, no false failures

✅ SQLite transactions for queue
   Atomic, race-condition-free, ACID compliant

✅ Metadata for linking
   Immutable references, audit trail, no database tables needed

✅ Event-driven recovery
   No polling, clean separation, composable

✅ Failure pattern detection
   Regex-based, category-based, suggests fixes

✅ Circular prevention
   Prevents repair-of-repair-bot infinite loops

PART 8: CRITICAL FACTS FOR PLANNING
================================================================================

TRANSACTIONAL SAFETY:
- All task queue operations wrapped in SQLite transactions
- No race conditions possible in task assignment
- ACID guarantees at database level

EVENT-DRIVEN (NOT POLLING):
- Recovery followup created by completion handler, not polling
- No delay, clean separation of concerns
- Scalable to many concurrent tasks

CONFIGURATION FLEXIBILITY:
- Recovery system can be enabled/disabled
- Dry-run mode for testing
- Failure categories extensible
- Circuit breaker thresholds configurable

NO AUTO-TIMEOUT DESIGN:
- Respects legitimate long-running tasks
- Manual intervention via manuallyTimeoutTask()
- Baseline learning mode collects duration stats
- Smart timeouts can be enabled after data collected

EXTENSIBLE PATTERNS:
- Metadata field (JSON in DB) for task linking
- Event hooks for pre/post-execution
- Transaction wrapper for atomic operations
- Logging with categories for filtering

================================================================================
CONCLUSION
================================================================================

The app-monitor architecture has a ROBUST FOUNDATION for recovery and resilience.

Rather than building new mechanisms, EXTEND EXISTING PATTERNS:

✓ Use metadata for linking (not new database tables)
✓ Use events for triggering (not polling loops)
✓ Use transactions for consistency (not ad-hoc locking)
✓ Use structured logging (already comprehensive)
✓ Use existing failure detection (extend categories)

Key Strengths:
- Event-driven (not polling)
- Transactional (atomic operations)
- Intelligent failure detection (categorized)
- Two-stage recovery (simple, proven)
- Extensible metadata (audit trails, linking)
- Comprehensive logging (20+ categories)

Key Gaps (Addressable):
- No recovery analytics
- No recovery budget tracking
- No workspace rollback
- Limited observability into recovery success rates

The system is PRODUCTION-READY and EXTENSIBLE.
